[NeverWrite](https://github.com/jsgrrchg/NeverWrite) is an Electron-based AI note-taking app — think Obsidian with an agent layer built in. I first came across it in [a post on r/ZedEditor](https://www.reddit.com/r/ZedEditor/comments/1t3nbgi/agentic_multipane_markdown_editor_inspired_by_zed/?utm_source=share&utm_medium=web3x&utm_name=web3xcss&utm_term=1&utm_content=share_button), someone mentioning it as an alternative worth watching.

I run Fedora. When I checked the releases page the Linux row was empty. Issue [#19](https://github.com/jsgrrchg/NeverWrite/issues/19) had been sitting open for a while with no one on it, and the CONTRIBUTING guide explicitly mentioned Linux as a wanted target.

So I took a crack at it. This ended up being my first open source contribution — and it got merged!

---

## The problem

NeverWrite isn't a pure JS app. It ships a Rust sidecar — a compiled binary that the Electron main process forks at runtime. That means getting Linux packaging working involved more than flipping a config flag:

- `electron-builder` needed AppImage targets for both `x64` and `arm64`
- The Rust sidecar staging scripts needed to cross-compile for Linux targets
- CI needed to run on `ubuntu-22.04` specifically — building on a newer runner produces a binary linked against a newer GLIBC, which then silently refuses to launch on most users' machines
- `electron-updater` needed a `latest-linux.yml` feed wired up so in-app updates would actually work
- The native menu bar shows up on Linux because NeverWrite uses a custom frameless titlebar designed for macOS — it needed to be hidden outside macOS and the window chrome needed platform-aware styling

---

## What I changed

The `electron-builder` config got Linux AppImage targets:

```json
"linux": {
  "target": [
    { "target": "AppImage", "arch": ["x64", "arm64"] }
  ],
  "icon": "build/icons/icon.png",
  "category": "Utility"
}
```

The staging scripts already handled macOS and Windows sidecars. I extended them to cross-compile the Rust binary for both Linux architectures before the Electron build runs, so the bundler can find the right binary for each target.

For CI, the only meaningful change was the runner:

```yaml
runs-on: ubuntu-22.04
```

`ubuntu-latest` at the time pointed to 24.04, which produces a GLIBC 2.38 baseline. Pinning to 22.04 drops that to 2.35 and covers the vast majority of current Linux installs without any code changes.

The titlebar fix was a conditional in the main process:

```ts
if (process.platform !== 'darwin') {
  win.setMenuBarVisibility(false)
}
```

Plus a CSS class applied to the drag region to account for the difference in compositing behavior between macOS and GTK.

---

## How the review went

The maintainer ([@jsgrrchg](https://github.com/jsgrrchg)) reviewed and jumped in directly — he added the updater feed configuration I'd left partially stubbed and wired the AppImage icon explicitly. We went back and forth over a day, he squashed the commits, and it merged on May 9th.

The PR ended up touching the builder config, staging scripts, CI workflow, main process window setup, and titlebar CSS. Seven commits total between the two of us.

## v0.2.5

The release shipped today. The Linux rows in the installer table are no longer empty:

| Platform | Architecture | Asset |
|----------|--------------|-------|
| Linux | x64 | `NeverWrite-0.2.5-x64.AppImage` |
| Linux | ARM64 | `NeverWrite-0.2.5-arm64.AppImage` |

In-app updates work on both. The window chrome looks correct. Cmd+W and its Linux equivalent both pass the shortcut tests.

The codebase was clean, the maintainer was responsive, and the problem was well-scoped. Not a bad way to open the account.
